# A2UI: interfaces the agent describes

The third learning doc in the [CopilotKit chat PRD package](../README.md). A2UI is **not** part of the first chat release; this page explains what it is, why it's interesting, and why it waits. The follow-on plan is the [A2UI PRD](../../a2ui/prd.md). Facts are sourced in [sources.md](../sources.md#a2ui), verified on 2026-09-13.

## The problem A2UI solves

In the first release, every weather widget is a component a developer wrote: the agent calls `get_daily_forecast`, and the chat renders our forecast component with the result. That is **controlled** generative UI — safe and polished, but every new kind of answer needs new code.

A2UI (Agent-to-User Interface) lets the agent **describe** a UI instead. The agent sends a declarative JSON description built from a catalog of components the client already trusts; the client renders it natively. No code is sent and nothing is executed. It was created by Google with contributions from CopilotKit, is Apache-2.0, and describes itself as an "early stage public preview".

| | Tool-call renderers (first release) | A2UI (later) |
| --- | --- | --- |
| Who designs the UI | A developer, per tool | The agent, per answer |
| Flexibility | Fixed per tool | Any composition of catalog components |
| Security surface | Only our components and a typed result | Untrusted layout and data, constrained by the catalog |
| Coupling | UI knows each tool's result shape | UI knows the catalog; the agent knows the format |
| Maturity | Stable in CopilotKit | Preview spec, no Angular 22 renderer, no .NET producer |

## The message model (v0.9.1)

A **surface** is one rendered region. The agent drives its lifecycle with four messages, and the client can send two back:

| Direction | Message | Purpose |
| --- | --- | --- |
| Agent → client | `createSurface` | Open a surface and name the catalog it uses |
| Agent → client | `updateComponents` | Send the component tree as a flat list, one of which has the id `root` |
| Agent → client | `updateDataModel` | Set data at a JSON Pointer path; components bind to paths |
| Agent → client | `deleteSurface` | Remove the surface |
| Client → agent | `action` | The user did something (for example pressed a button) |
| Client → agent | `error` | The client couldn't render or validate what it received |

An illustrative forecast surface — the exact schema lives in the [v0.9.1 specification](https://a2ui.org/specification/v0.9.1-a2ui/):

```jsonc
// Illustrative only — check the specification for exact property names.
{ "createSurface":   { "surfaceId": "forecast-1", "catalogId": "<basic catalog id>" } }
{ "updateComponents": { "surfaceId": "forecast-1", "components": [
    { "id": "root",  "component": "Card",   "child": "body" },
    { "id": "body",  "component": "Column", "children": ["title", "days"] },
    { "id": "title", "component": "Text",   "text": { "path": "/location" } },
    { "id": "days",  "component": "List",   "children": { "path": "/days", "componentId": "day" } },
    { "id": "day",   "component": "Text",   "text": { "path": "summary" } }
] } }
{ "updateDataModel": { "surfaceId": "forecast-1", "path": "/",
    "value": { "location": "Seattle", "days": [ { "summary": "Mon · Showers · 12 °C" } ] } } }
```

The structure (components) and the data (data model) are separate, so the agent can update a temperature without resending the layout.

## Catalogs and the security model

A **catalog** is the list of components a client is willing to render. The basic catalog has 18: Text, Image, Icon, Video, AudioPlayer, Row, Column, List, Card, Tabs, Modal, Divider, Button, TextField, CheckBox, ChoicePicker, Slider and DateTimeInput. Clients advertise which catalogs they support; the agent may only use those components.

Being declarative removes the worst risk — the agent can't ship code — but a surface is still untrusted input. The Angular renderer's own README warns about spoofed interfaces (phishing), script injection through property values, and denial of service through huge layouts. A production renderer validates every message against the catalog schema, sanitizes text, refuses remote media that isn't allow-listed, and caps surface size.

## How A2UI travels

| Transport | How | Fit for this repository today |
| --- | --- | --- |
| A2A extension | A2UI messages as `application/a2ui+json` data parts | The chat doesn't use A2A |
| AG-UI | Surfaces arrive as `ACTIVITY_SNAPSHOT` events with `activityType: "a2ui-surface"`, produced by `@ag-ui/a2ui-middleware` | The middleware is **server-side Node** (it imports `node:crypto`) and injects a `render_a2ui` **client tool** — the design has no Node server, and the API guard rejects client tools |

## Renderers

| Renderer | Status | Fit |
| --- | --- | --- |
| `@a2ui/angular` 0.10.7 | Official; signals-based | **Peers Angular `^21.2.5`**; the app is on Angular 22.1, and no Angular 22 issue or pull request exists |
| `@a2ui/web_core` 0.11.0 | Framework-neutral core with no peer dependencies | Could back a custom Bootstrap renderer of the basic catalog |
| `@a2ui/lit`, `@a2ui/react`, Flutter | Official | Not Angular |
| CopilotKit's A2UI activity renderer | Ships in `@copilotkit/angular` | Unverified without CopilotKit's runtime — an open question in the A2UI PRD |

## Producing A2UI on the agent side

- The only agent SDK is **Python** (`a2ui-agent-sdk`); Microsoft Agent Framework supports A2UI in **Python only**.
- The .NET host emits no A2UI, and no official .NET A2UI package is published. Two .NET routes are plausible but unproven: a tool whose result carries A2UI operations that the client renders, or an `AGUIStreamOptions` mapping that turns a tool result into an `ACTIVITY_SNAPSHOT` (undocumented for .NET).
- Sending a user's `action` back needs an API contract change, because the input guard rejects `forwardedProps` and `state`.

## Maturity

The spec is v0.9.1 with v1.0 as a release candidate that adds function calls and changes theming. Expect breaking changes before 1.0 is final.

## When we'd adopt it

Adopt A2UI when these line up — each is a revisit trigger in [decisions.md](../decisions.md#revisit-triggers):

- an Angular 22–compatible renderer (official or our own on `@a2ui/web_core`),
- a way for the .NET agent to produce surfaces,
- an agreed contract for user actions through the input guard,
- A2UI 1.0 final, or acceptance of pre-1.0 churn.

The [A2UI PRD](../../a2ui/prd.md) breaks this into epics.
